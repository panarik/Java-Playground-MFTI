# Бины Spring. Инверсия зависимостей

Как устроен пример. Запуск, компиляция и запросы лежат в корневом `README.md`, раздел «Семинар по спрингу».

Контейнер Spring собирает бины: сервис зависит от интерфейса `Notifier`, счётчик один на все потоки. Тот же контейнер принимает `POST /order` и раскладывает тело по бинам отделов. Голый сервер в пакете `mfti.lessons.springPatterns.plain` принимает те же тела, но оба отдела сидят в одном методе.

---

## Что такое бин

Бин — объект, которым владеет контейнер Spring.

Контейнер сам вызывает конструктор, хранит ссылку и передаёт её туда, где она указана в параметрах другого конструктора. Бины этого примера:

| Класс | Пакет | Зачем |
|---|---|---|
| `EmailNotifier` | `notification` | отправляет уведомление |
| `OrderService` | `service` | оформляет заказ и просит `Notifier` отправить сообщение |
| `BookDepartment`, `ConstructionDepartment` | `department` | решают, их ли текст запроса, и возвращают свою строку ответа |
| `OrderController` | `controller` | принимает `POST /order` и обходит бины `Department` |
| `SharedCounter` | `demo` | общий счётчик для нескольких потоков |
| `DemoRunner` | `demo` | сценарий, который контейнер запускает после создания остальных бинов |

По умолчанию бин один на весь контейнер. Такой режим называется singleton. Конструктор отрабатывает один раз за запуск. В логе строка «контейнер создал…» у каждого класса встречается один раз, хотя заказов может быть много, а прибавлений к счётчику 160.

`main` этих объектов не создаёт. Он делает только это:

```java
SpringApplication.run(BeansApplication.class, args);
```

Дальше работает контейнер.

1. Находит классы с `@Component`, `@Service` и `@RestController` в пакете `mfti.lessons.springPatterns.beans` и во вложенных: `controller`, `service`, `notification`, `department`, `demo`.
2. Создаёт `EmailNotifier`: его конструктор пустой, ждать некого.
3. Создаёт `OrderService`, `BookDepartment` и `ConstructionDepartment` и кладёт в их конструкторы уже готовый `EmailNotifier`. В логе совпадают числа объектов: все трое получили тот самый экземпляр.
4. Создаёт `OrderController` и передаёт ему список всех бинов типа `Department`.
5. Создаёт `SharedCounter` и `DemoRunner`.
6. Поднимает HTTP-сервер и сам вызывает `DemoRunner.run`.

Порядок пунктов контейнер выбирает сам. Зависимость он соблюдает всегда: класс появится после тех бинов, которые написаны в его конструкторе.

Число после «объект» — это `identityHashCode`. Оно меняется от запуска к запуску. Совпадение чисел внутри одного запуска и есть доказательство, что передали тот же экземпляр.

## Что такое компонент

Компонент — класс, который контейнер должен найти при старте и превратить в бин.

- `@Component` — общая пометка. Она стоит на `EmailNotifier`, отделах, `SharedCounter` и `DemoRunner`.
- `@Service` стоит на `OrderService`. Для контейнера это тот же `@Component`: аннотация `@Service` сама помечена `@Component`. Имя `@Service` нужно человеку, чтобы видеть «это бизнес-операция».
- `@RestController` стоит на `OrderController`. Для контейнера это тоже `@Component`. Дополнительно методы с `@PostMapping` становятся HTTP-ручками. Сам класс при этом один singleton. Ручка — метод `order`, не весь объект.

`@Order` бин не создаёт. Она задаёт место бина в списке, когда контейнер собирает `List<Department>`.

Имя бина контейнер берёт из имени класса и делает первую букву маленькой: класс `EmailNotifier` становится бином `emailNotifier`.

Поиск начинается с пакета класса, на котором висит `@SpringBootApplication`, и идёт во вложенные пакеты. Класс с `@Component` в другом корневом пакете контейнер не увидит. Компиляция при этом пройдёт, старт — нет. Это тот же эффект, что в эксперименте ниже.

`@Autowired` на конструкторе нет сознательно. Если у бина один конструктор, Spring начиная с 4.3 подставляет аргументы сам.

## Инверсия зависимостей

Зависимость — это кто про кого знает в коде.

Сервис мог бы создать почту сам:

```java
public class OrderService {
    private final Notifier notifier = new EmailNotifier();

    public void place(String item) {
        notifier.send("заказ оформлен: " + item);
    }
}
```

Тогда `OrderService` знает конкретный класс. Удаление `EmailNotifier.java` ломает компиляцию сервиса. Замена письма на SMS — это правка сервиса.

В проекте стрелка развёрнута к интерфейсу:

```text
OrderService  ──зависит от──▶  Notifier  ◀──реализует──  EmailNotifier
```

Верхний уровень зависит от `Notifier`. Нижний уровень тоже зависит от `Notifier`, потому что реализует его. Конкретную пару знает контейнер: он один создаёт `EmailNotifier` и передаёт его в конструктор `OrderService`.

Проверка на исходнике: в `OrderService.java` есть поле типа `Notifier` и нет импорта `EmailNotifier`. Сервис компилируется без файла реализации.

Та же стрелка у отделов. `OrderController` зависит от `Department` и получает `List<Department>`. Слов «книга» и «бульдозер» в контроллере нет. Их проверяют методы `matches` у бинов `BookDepartment` и `ConstructionDepartment`. Контроллер передаёт им текст тела запроса и складывает возвращённые строки. Никто не перезаписывает чужую.

Рядом стоят три разных термина. В этом проекте они видны по отдельности.

- Инверсия управления. `main` не вызывает `DemoRunner.run`. После сборки бинов контейнер вызывает `run` сам.
- Внедрение зависимости. `Notifier` приходит аргументом конструктора. Сервис его не создаёт через `new`.
- Инверсия зависимостей. Сервис зависит от интерфейса `Notifier`, а реализация `EmailNotifier` зависит от того же интерфейса. Стрелка от сервиса к конкретному классу развёрнута.

Внедрение — способ передать объект. Инверсия зависимостей — от какого типа этот объект объявлен. Контейнер умеет внедрить и конкретный класс. Учебный смысл примера в том, что в конструктор объявлен интерфейс.

## Голый сервер рядом

`PlainOrderServer` только поднимает сервер и передаёт ему объект `OrderHandler`. Это не бин и не Spring. Оба отдела дописали по `if` в один метод `OrderHandler.handle` и пишут в одну переменную `reply`.

По отдельности каждый проверил только своё слово. Запрос, в котором есть оба слова, проходит оба `if`. Строительный отдел затирает ответ книжного: кто ниже в методе, тот и остаётся в ответе клиенту. Книжный отдел своё условие не менял. Его ответ стёрла чужая ветка в том же методе.

Так и выглядит сильная связанность в команде. Нет шва, куда второй человек мог бы встать рядом. Он входит в общий код и пишет в те же переменные. Поменять порядок `if`, дописать `else` или выйти из метода через `return` — и соседний отдел перестаёт получать свой ответ, хотя его условие по-прежнему истинно.

Одна ответственность здесь тоже одна на двоих. Повод менять `handle` есть у обоих отделов, плюс у того, кто отвечает за HTTP. У `OrderService.place` повод один: как оформляется заказ, и отделы туда своим `if` не входят. В Spring новый отдел — новый класс с `@Component`. Метод контроллера при этом не меняют.

## Эксперимент 1. Снять компонент: Java собирается, Spring не стартует

Компилятор и контейнер проверяют разное.

Компилятор смотрит типы. Конструктор `OrderService` принимает `Notifier`. Интерфейс на месте, значит файл сервиса законен. Есть ли у Spring живой объект этого типа, `javac` не знает.

Контейнер смотрит бины в момент старта. Он читает конструктор `OrderService`, видит параметр `Notifier` и ищет бин такого типа. Бин появляется только из класса с `@Component` или `@Service`.

Если убрать `@Component` с `EmailNotifier` и оставить сам класс, сборка проходит. Старт падает до строки `Started BeansApplication`:

```text
Parameter 0 of constructor in mfti.lessons.springPatterns.beans.service.OrderService required a bean of type 'mfti.lessons.springPatterns.beans.notification.Notifier' that could not be found.
```

`Parameter 0` — первый аргумент конструктора, это `Notifier`. Фраза `that could not be found` означает: подходящего бина в контейнере нет. Класс `EmailNotifier` в classpath есть, но без `@Component` контейнер не считает его бином.

Тот же результат будет, если удалить файл `EmailNotifier.java` целиком. Компиляция жива, потому что на этот файл никто из оставшегося кода не ссылается. Старт мёртв, потому что реализовать `Notifier` стало нечем.

Аннотацию после эксперимента нужно вернуть, иначе следующие старты будут падать так же.

## Эксперимент 2. Две реализации того же интерфейса

Инверсия зависимостей здесь видна с другой стороны. Сервису подходит любой `Notifier`. Контейнеру нужно выбрать один.

Если скопировать `EmailNotifier` в новый класс `SmsNotifier`, оставить на нём `@Component` и `implements Notifier`, сборка снова проходит: сервис по-прежнему видит только интерфейс. Старт падает с другим текстом:

```text
Parameter 0 of constructor in mfti.lessons.springPatterns.beans.service.OrderService required a single bean, but 2 were found:
	- emailNotifier
	- smsNotifier
```

Java молчит, потому что оба класса законно реализуют один интерфейс. Spring отказывается выбирать сам.

Дальше по тексту Spring бывает абзац про флаг компилятора `-parameters`. Это общая подсказка отчёта. Причина падения записана выше: бинов два, а параметр один.

Как выбирают вручную, если это понадобится дальше по курсу:

- `@Primary` на одной из реализаций — контейнер берёт её, когда подходит несколько бинов;
- `@Qualifier("emailNotifier")` на параметре конструктора — берётся бин с этим именем.

Файл `SmsNotifier.java` после эксперимента нужно удалить. Иначе проект не поднимется. Если класс уже успели собрать, нужен `mvn clean`: старый `.class` в `target` контейнер тоже подхватывает.

## Многопоточка

У singleton-бина одна ссылка на все потоки.

Каждый HTTP-запрос Tomcat обрабатывает отдельный поток, и все эти потоки входят в те же бины контроллера и сервиса. Чтобы увидеть это без нагрузки извне, `DemoRunner` сам запускает пул из 8 потоков.

На что смотреть в логе. Имена потоков стоят в квадратных скобках.

```text
[main]            контейнер создал SharedCounter, объект 1967432164
[main]            --- один бин SharedCounter, объект SharedCounter@1967432164 ---
[pool-2-thread-1] поток pool-2-thread-1 работает с тем же бином SharedCounter@1967432164
[pool-2-thread-8] поток pool-2-thread-8 работает с тем же бином SharedCounter@1967432164
[main]            без синхронизации: потоков 8, прибавлений на поток 20, ожидаем 160, в бине 20
[main]            с синхронизацией: потоков 8, прибавлений на поток 20, ожидаем 160, в бине 160
```

Конструктор счётчика отработал в `main` один раз. Все восемь рабочих потоков печатают тот же `SharedCounter@...`. Это не восемь счётчиков.

Дальше два прохода по 160 прибавлений. Методы `addUnsafe` и `addSafe` одинаковые: прочитали поле, подождали 2 миллисекунды, записали «прочитанное + 1». У второго метода на сигнатуре стоит `synchronized`.

Без синхронизации в прогоне в бине осталось 20 из 160. Пока один поток спит между чтением и записью, остальные читают то же старое число и потом затирают друг друга. Чья запись прошла последней, та и сохранилась. Точное число от запуска к запуску плавает, до 160 оно не дотягивает.

С `synchronized` в бине 160. В этот кусок кода входит один поток, остальные ждут на замке объекта. Пауза та же, потерь нет.

Пауза `Thread.sleep(2)` нужна только для занятия. Она расширяет окно между чтением и записью, чтобы потеря случилась на первом запуске. В боевом коде гонка есть и без сна: два потока читают одно значение и оба пишут его плюс один.

Отсюда правило для бинов. Контейнер не выдаёт потоку личную копию singleton-бина.

- `OrderService` своего изменяемого поля не хранит. Один бин можно вызывать из многих потоков: делить им нечего.
- `SharedCounter` хранит `value`. Такой бин либо защищает поле (`synchronized`, `AtomicInteger`, замок), либо его нельзя делать общим.

`synchronized` на `addSafe` запирает сам объект бина. Для учебного счётчика этого хватает. Если у бина два независимых поля, один замок на весь объект их всё равно сериализует. Это уже тема прошлой многопоточности, не Spring.
