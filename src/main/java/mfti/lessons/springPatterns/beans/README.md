# Бины Spring. Инверсия зависимостей

Учебный проект на Spring Boot 3.5 и Java 21. Классы лежат в source root IDEA: `src/main/java/mfti/lessons/springPatterns/beans`. Запускаются из корневого `pom.xml`.

В программе два показа на одном заказе. Контейнер Spring собирает бины: сервис зависит от интерфейса `Notifier`, счётчик один на все потоки. Тот же контейнер слушает `POST /order` на порту 8081 и раскладывает тело по бинам отделов. Рядом голый сервер на порту 8080 принимает те же тела, но оба отдела сидят в одном методе.

Команды запускать из корня репозитория. Приглашение оболочки должно заканчиваться на `Java-Playground-MFTI`, не на `beans`. Из этой папки Maven не видит `pom.xml` и пишет `No plugin found for prefix 'spring-boot'`. Это не сломанный бин. Выйти в корень:

```bash
cd "$(git rev-parse --show-toplevel)"
```

Компиляция. Контейнер не запускается, наличие бина `Notifier` не проверяется. Успех — строка `BUILD SUCCESS` в конце. Снятый `@Component` с `EmailNotifier` эту команду не ломает.

```bash
mvn -DskipTests compile
```

Старт. Здесь Spring создаёт бины. Без `@Component` на `EmailNotifier` падает эта команда, компиляция при этом уже прошла.

```bash
mvn spring-boot:run
```

Класс с `main`: `mfti.lessons.springPatterns.beans.BeansApplication`. После строки `Started BeansApplication` сервер остаётся на `localhost:8081`. Голый сервер запускается отдельно, он описан ниже.

## Что такое бин

Бин — объект, которым владеет контейнер Spring.

Контейнер сам вызывает конструктор, хранит ссылку и передаёт её туда, где она указана в параметрах другого конструктора. В этом проекте четыре бина:

| Класс | Зачем |
|---|---|
| `EmailNotifier` | отправляет уведомление |
| `OrderService` | оформляет заказ и просит `Notifier` отправить сообщение |
| `SharedCounter` | общий счётчик для нескольких потоков |
| `DemoRunner` | сценарий, который контейнер запускает после создания остальных бинов |

По умолчанию бин один на весь контейнер. Такой режим называется singleton. Конструктор отрабатывает один раз за запуск. В логе строка «контейнер создал…» у каждого класса встречается один раз, хотя заказ один, а прибавлений к счётчику 160.

`main` этих объектов не создаёт. Он делает только это:

```java
SpringApplication.run(BeansApplication.class, args);
```

Дальше работает контейнер.

1. Находит классы с `@Component` и `@Service` в пакете `mfti.lessons.springPatterns.beans` и во вложенных: `controller`, `service`, `notification`, `department`, `demo`.
2. Создаёт `EmailNotifier`: его конструктор пустой, ждать некого.
3. Создаёт `OrderService` и кладёт в конструктор уже готовый `EmailNotifier`. В логе совпадают числа объектов: сервис получил тот самый экземпляр.
4. Создаёт `SharedCounter` и `DemoRunner`.
5. Сам вызывает `DemoRunner.run`.

Порядок пунктов 2 и 4 контейнер выбирает сам. Зависимость он соблюдает всегда: `OrderService` появится после `EmailNotifier`, `DemoRunner` — после обоих своих аргументов.

Число после «объект» — это `identityHashCode`. Оно меняется от запуска к запуску. Совпадение чисел внутри одного запуска и есть доказательство, что передали тот же экземпляр.

## Что такое компонент

Компонент — класс, который контейнер должен найти при старте и превратить в бин.

- `@Component` — общая пометка. Она стоит на `EmailNotifier`, `SharedCounter` и `DemoRunner`.
- `@Service` стоит на `OrderService`. Для контейнера это тот же `@Component`: аннотация `@Service` сама помечена `@Component`. Имя `@Service` нужно человеку, чтобы видеть «это бизнес-операция».
- `@Repository` и `@Controller` устроены так же. Здесь их нет, чтобы в логе не было веб-сервера и базы.

Имя бина контейнер берёт из имени класса и делает первую букву маленькой: класс `EmailNotifier` становится бином `emailNotifier`.

Поиск начинается с пакета класса, на котором висит `@SpringBootApplication`, и идёт во вложенные пакеты. Класс с `@Component` в другом корневом пакете контейнер не увидит. Компиляция при этом пройдёт, старт — нет. Это тот же эффект, что в эксперименте ниже.

`@Autowired` на конструкторе нет сознательно. Если у бина один конструктор, Spring начиная с 4.3 подставляет аргументы сам.

## Инверсия зависимостей

Зависимость — это кто про кого знает в коде.

Сервис мог бы создать почту сам:

```java
public class OrderService {
    private final Notifier notifier = new EmailNotifier();

    public void place(String item) {
        notifier.send("заказ оформлен: " + item);
    }
}
```

Тогда `OrderService` знает конкретный класс. Удаление `EmailNotifier.java` ломает компиляцию сервиса. Замена письма на SMS — это правка сервиса.

В проекте стрелка развёрнута к интерфейсу:

```text
OrderService  ──зависит от──▶  Notifier  ◀──реализует──  EmailNotifier
```

Верхний уровень зависит от `Notifier`. Нижний уровень тоже зависит от `Notifier`, потому что реализует его. Конкретную пару знает контейнер: он один создаёт `EmailNotifier` и передаёт его в конструктор `OrderService`.

Проверка на исходнике: в `OrderService.java` есть поле типа `Notifier` и нет импорта `EmailNotifier`. Сервис компилируется без файла реализации.

Рядом стоят три разных термина. В этом проекте они видны по отдельности.

- Инверсия управления. `main` не вызывает `DemoRunner.run`. После сборки бинов контейнер вызывает `run` сам.
- Внедрение зависимости. `Notifier` приходит аргументом конструктора. Сервис его не создаёт через `new`.
- Инверсия зависимостей. Сервис зависит от интерфейса `Notifier`, а реализация `EmailNotifier` зависит от того же интерфейса. Стрелка от сервиса к конкретному классу развёрнута.

Внедрение — способ передать объект. Инверсия зависимостей — от какого типа этот объект объявлен. Контейнер умеет внедрить и конкретный класс. Учебный смысл примера в том, что в конструктор объявлен интерфейс.

## Для сравнения: сервер на пакете JDK

Рядом, уже в основном проекте, лежит пакет `mfti.lessons.springPatterns.plain`. Это не бин и не Spring: класс `PlainOrderServer` поднимает сервер из `com.sun.net.httpserver`. Сканер `@SpringBootApplication` его не видит, пакет другой.

Запуск из корня репозитория:

```bash
mvn compile exec:java@plain-server
```

Два отдела пишут в один метод `handle`. У каждого свой объект, но тело запроса, письмо и переменная `reply` общие.

Книжный отдел: если в теле есть `книга`, создаётся `BookDepartment`. Строительный: если есть `бульдозер`, создаётся `ConstructionDepartment`. Второй `if` стоит ниже и пишет в ту же `reply`.

По отдельности каждый проверил только своё слово.

```bash
curl -d 'книга' http://localhost:8080/order
```

Ответ: `принят в книжный: книга`. В консоли: `письмо: книжный отдел: книга`.

```bash
curl -d 'бульдозер' http://localhost:8080/order
```

Ответ: `принят на стройку: бульдозер`. В консоли: `письмо: строительный отдел: бульдозер`.

Запрос, в котором есть оба слова, проходит оба `if`. Строительный отдел затирает ответ книжного, писем уходит два:

```bash
curl -d 'книга про бульдозер' http://localhost:8080/order
```

Ответ: `принят на стройку: книга про бульдозер`. В консоли сначала письмо книжного отдела, потом письмо строительного. Клиент видит только стройку. Книжный отдел свой запрос не ломал: его сломала чужая ветка ниже по тому же методу.

Так и выглядит сильная связанность в команде. Нет шва, куда второй человек мог бы встать рядом. Он входит в общий код и пишет в те же переменные. Поменять порядок `if`, дописать `else` или выйти из метода через `return` — и соседний отдел перестаёт получать свой ответ, хотя его условие по-прежнему истинно.

Одна ответственность здесь тоже одна на двоих. Повод менять `handle` есть у обоих отделов, плюс у того, кто отвечает за HTTP. У `OrderService.place` повод один: как оформляется заказ, и отделы туда своим `if` не входят.

Те же три тела принимает Spring на порту 8081. Слова отделов лежат в `BookDepartment` и `ConstructionDepartment`, контроллер их не содержит. На `книга про бульдозер` Spring возвращает обе строки, голый сервер — только последнюю. Запросы и ожидаемые ответы собраны в корневом `README.md`, раздел «Семинар по спрингу».

## Эксперимент 1. Снять компонент: Java собирается, Spring не стартует

Компилятор и контейнер проверяют разное.

Компилятор смотрит типы. Конструктор `OrderService` принимает `Notifier`. Интерфейс на месте, значит файл сервиса законен. Есть ли у Spring живой объект этого типа, `javac` не знает.

Контейнер смотрит бины в момент старта. Он читает конструктор `OrderService`, видит параметр `Notifier` и ищет бин такого типа. Бин появляется только из класса с `@Component` или `@Service`.

Шаги на занятии.

1. Удалите строку `@Component` над классом `EmailNotifier`. Сам класс и интерфейс оставьте.
2. Соберите проект:

```bash
mvn -DskipTests compile
```

Сборка проходит. `OrderService` по-прежнему ссылается на интерфейс, а не на `EmailNotifier`.
3. Запустите:

```bash
mvn spring-boot:run
```

Приложение падает до строки `Started BeansApplication`. Контейнер пишет:

```text
***************************
APPLICATION FAILED TO START
***************************

Description:

Parameter 0 of constructor in mfti.lessons.springPatterns.beans.service.OrderService required a bean of type 'mfti.lessons.springPatterns.beans.notification.Notifier' that could not be found.

Action:

Consider defining a bean of type 'mfti.lessons.springPatterns.beans.notification.Notifier' in your configuration.
```

`Parameter 0` — первый аргумент конструктора, это `Notifier`. Фраза `that could not be found` означает: подходящего бина в контейнере нет. Класс `EmailNotifier` в classpath есть, но без `@Component` контейнер не считает его бином.

Тот же результат будет, если удалить файл `EmailNotifier.java` целиком. Компиляция жива, потому что на этот файл никто из оставшегося кода не ссылается. Старт мёртв, потому что реализовать `Notifier` стало нечем.

Верните `@Component`, иначе следующие запуски будут падать так же.

## Эксперимент 2. Две реализации того же интерфейса

Инверсия зависимостей здесь видна с другой стороны. Сервису подходит любой `Notifier`. Контейнеру нужно выбрать один.

Скопируйте `EmailNotifier` в новый класс `SmsNotifier`, оставьте на нём `@Component` и `implements Notifier`. `OrderService` не меняйте.

```bash
mvn -DskipTests compile
```

Сборка проходит: сервис по-прежнему видит только интерфейс.

```bash
mvn spring-boot:run
```

Старт падает с другим текстом:

```text
Description:

Parameter 0 of constructor in mfti.lessons.springPatterns.beans.service.OrderService required a single bean, but 2 were found:
	- emailNotifier: defined in file [.../EmailNotifier.class]
	- smsNotifier: defined in file [.../SmsNotifier.class]

Action:

Consider marking one of the beans as @Primary, updating the consumer to accept multiple beans, or using @Qualifier to identify the bean that should be consumed
```

Java молчит, потому что оба класса законно реализуют один интерфейс. Spring отказывается выбирать сам.

Дальше по тексту Spring бывает абзац про флаг компилятора `-parameters`. Это общая подсказка отчёта. Причина падения записана выше: бинов два, а параметр один.

Как выбирают вручную, если это понадобится дальше по курсу:

- `@Primary` на одной из реализаций — контейнер берёт её, когда подходит несколько бинов;
- `@Qualifier("emailNotifier")` на параметре конструктора — берётся бин с этим именем.

Для этого занятия файл `SmsNotifier.java` после эксперимента удалите. Иначе проект не поднимется. Если класс уже успели собрать, выполните `mvn clean`: старый `.class` в `target` контейнер тоже подхватывает.

## Многопоточка

У singleton-бина одна ссылка на все потоки.

В обычном веб-приложении Spring каждый HTTP-запрос обрабатывает отдельный поток сервера, и все эти потоки входят в те же бины контроллера и сервиса. Здесь сервера нет. `DemoRunner` сам запускает пул из 8 потоков, чтобы в одном логе было видно то же правило.

На что смотреть в логе. Имена потоков стоят в квадратных скобках.

```text
[main]            контейнер создал SharedCounter, объект 1967432164
[main]            --- один бин SharedCounter, объект SharedCounter@1967432164 ---
[pool-2-thread-1] поток pool-2-thread-1 работает с тем же бином SharedCounter@1967432164
[pool-2-thread-2] поток pool-2-thread-2 работает с тем же бином SharedCounter@1967432164
...
[pool-2-thread-8] поток pool-2-thread-8 работает с тем же бином SharedCounter@1967432164
[main]            без синхронизации: потоков 8, прибавлений на поток 20, ожидаем 160, в бине 20
[main]            с синхронизацией: потоков 8, прибавлений на поток 20, ожидаем 160, в бине 160
```

Конструктор счётчика отработал в `main` один раз. Все восемь рабочих потоков печатают тот же `SharedCounter@...`. Это не восемь счётчиков.

Дальше два прохода по 160 прибавлений. Методы `addUnsafe` и `addSafe` одинаковые: прочитали поле, подождали 2 миллисекунды, записали «прочитанное + 1». У второго метода на сигнатуре стоит `synchronized`.

Без синхронизации в прогоне в бине осталось 20 из 160. Пока один поток спит между чтением и записью, остальные читают то же старое число и потом затирают друг друга. Чья запись прошла последней, та и сохранилась. Точное число от запуска к запуску плавает, до 160 оно не дотягивает.

С `synchronized` в бине 160. В этот кусок кода входит один поток, остальные ждут на замке объекта. Пауза та же, потерь нет.

Пауза `Thread.sleep(2)` нужна только для занятия. Она расширяет окно между чтением и записью, чтобы потеря случилась на первом запуске. В боевом коде гонка есть и без сна: два потока читают одно значение и оба пишут его плюс один. Поймать такую ошибку тестом труднее, на семинаре по пулу потоков это уже разбиралось.

Отсюда правило для бинов. Контейнер не выдаёт потоку личную копию singleton-бина.

- `OrderService` своего изменяемого поля не хранит. Один бин можно вызывать из многих потоков: делить им нечего.
- `SharedCounter` хранит `value`. Такой бин либо защищает поле (`synchronized`, `AtomicInteger`, замок), либо его нельзя делать общим.

`synchronized` на `addSafe` запирает сам объект бина. Для учебного счётчика этого хватает. Если у бина два независимых поля, один замок на весь объект их всё равно сериализует. Это уже тема прошлой многопоточности, не Spring.

## Что сделать на занятии

1. Запустить `mvn spring-boot:run` из корня репозитория и по логу пройти создание бинов: одинаковые номера объектов у `EmailNotifier` и у аргумента `OrderService`.
2. Снять `@Component` с `EmailNotifier`, убедиться, что `compile` проходит, а `spring-boot:run` падает с `required a bean of type 'mfti.lessons.springPatterns.beans.notification.Notifier'`. Вернуть аннотацию.
3. Добавить второй `@Component` на реализацию `Notifier`, увидеть `required a single bean, but 2 were found`. Удалить лишний класс и сделать `mvn clean`.
4. В логе счётчика показать один `SharedCounter@...` на восьми потоках, итог 160 и итог меньше 160.
5. Отдельной командой из корня `mvn compile exec:java@plain-server` поднять голый сервер. Сначала три тела на `localhost:8081`, потом те же три на `localhost:8080`. На `книга про бульдозер` у Spring в ответе две строки, у голого сервера одна: нижний `if` затёр `reply`.
