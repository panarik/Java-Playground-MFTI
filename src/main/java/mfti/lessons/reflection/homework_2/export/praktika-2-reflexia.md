# Практика №2. Рефлексия

Это задание про то, как написать свой маленький инструмент поверх чужого кода. Чужой класс мы не переписываем. Мы смотрим на него через рефлексию, читаем аннотации и подменяем объект обёрткой, которая перехватывает вызовы методов.

В задании три части.

- Задание 1. Кэширование. Обязательное, вместе с заданием 2 даёт 6 баллов.
- Задание 2. Свой мини-JUnit. Обязательное.
- Задание 3. Плагин сборки, который запускает эти тесты. Необязательное, +1 балл.

После сдачи будет собеседование по теме, ещё до 6 баллов.

# Зачем в этой домашке рефлексия

Аннотация сама код не запускает. `@Cache` на методе — это стикер «этот результат можно запоминать». Пока программа работает, стикер просто висит на методе. Сам он никого не заставляет пропустить повторный вызов.

Рефлексия — это способ во время работы программы узнать, что лежит в чужом объекте, и вызвать это. Студент пишет один утилитный метод. Этот метод заранее не знает, какой класс ему принесут: сегодня `A`, завтра дробь, послезавтра класс с запросом в базу. Имена методов тоже заранее неизвестны. Узнать их можно только у уже созданного объекта, когда программа запущена. Для этого и нужна рефлексия.

Если бы кэш писали внутри конкретного класса `A`, рефлексия была бы не нужна. Автор `A` и так знает свои методы и может сам завести поле `cachedValue`. Домашка про другое: кэш добавляется снаружи, к любому готовому объекту, без правки его исходников. То же самое со второй частью: `TestRunner` запускает тесты любого класса, который ему передали. Имена тестовых методов он в свой код не вписывает.

Что именно студент делает рефлексией:

1. Узнать реальный класс объекта: `object.getClass()`. Ссылка снаружи может иметь тип интерфейса `Able`, а аннотации лежат на классе `A`.
2. Получить список методов этого класса: `getMethods()` или `getDeclaredMethods()`.
3. Прочитать аннотацию на методе: `isAnnotationPresent`, `getAnnotation`. Так код отличает метод, который надо кэшировать, от метода, который сбрасывает кэш, и от обычного метода.
4. Вызвать метод, имя которого в вашей программе не записано: `method.invoke(object)`. Обёртка не пишет `a.method()`. Она получает объект `Method` и вызывает тот метод, который пришёл в этот вызов.
5. Собрать обёртку, которая снаружи выглядит как исходный объект. Для этого берут интерфейсы реального класса и создают динамический прокси: `Proxy.newProxyInstance`. Каждый вызов метода на прокси приходит в ваш `InvocationHandler` уже как объект `Method`. Дальше снова пункты 3 и 4.

Во второй части тот же набор действий, только цель другая. `TestRunner` получает `Class<?>`. Рефлексией он создаёт объект этого класса (`getDeclaredConstructor().newInstance()`), находит методы с `@Test` и остальными аннотациями, читает имя теста и приоритет, проверяет, статический метод или нет, и запускает метод через `invoke`.

Без этих вызовов аннотации остаются комментариями для человека. Программа их не видит и чужой метод по имени, которого нет в исходнике утилиты, не вызовет.

# Задание 1. Кэширование

## О чём это, простыми словами

Есть объект. У него есть метод, который что-то считает. 
Считать долго или дорого, а результат при тех же данных всегда один и тот же.

Кэш — это память «я это уже считал». 
Первый раз метод выполняется по-настоящему. 
Второй раз, если объект с тех пор не меняли, метод не вызывают: возвращают уже посчитанное значение.

## Пример из жизни: 
Калькулятор на телефоне. 
Вы нажали `2 + 2`, он показал `4`. 
Если ничего не менять и снова спросить тот же пример, заново складывать не нужно: ответ уже известен. 
Но если вы стёрли экран и ввели другие числа, старый ответ больше не годится. Его надо забыть и посчитать заново.

То же самое бывает в программах:

- дробь `2/5`. Метод `doubleValue()` каждый раз делит 2 на 5 и получает `0.4`. Пока числитель и знаменатель те же, делить заново незачем;
- запрос к базе. Первый раз идём в базу и ждём. Пока данные не изменились, отдаём то, что уже прочитали;
- браузер. Картинку сайта он скачал один раз. Пока страница та же, он берёт её с диска, а не качает снова.

## Что нужно сделать

Нужен утилитный метод примерно такого вида:

```java
public static <T> T cache(T object);
```

Он принимает любой объект и возвращает другой объект того же типа. 
Снаружи это выглядит как тот же объект: у него те же методы. 
Внутри это обёртка. Она перехватывает вызовы и решает, звать оригинальный метод или отдать сохранённый результат.

Сам класс, который вам дали, менять не нужно. Логику кэша вы не вписываете внутрь `method()`. Вы добавляете её снаружи, методом `cache`.

## Как выглядит пример из задания

Есть интерфейс и класс:

```java
interface Able {
    void method();
    void setValue();
}

class A implements Able {
    @Cache
    @Override
    public void method() {
        System.out.println("original method");
    }

    @Setter
    @Override
    public void setValue() {
        System.out.println("seter method");
    }
}
```

И такой запуск:

```java
Able a = Utils.cache(new A());

a.method();    // печатает: original method
a.method();    // ничего не печатает
a.setValue();  // печатает: seter method
a.setValue();  // печатает: seter method
a.method();    // печатает: original method
```

Разбор по строкам.

1. `Utils.cache(new A())` создаёт обёртку вокруг нового `A`. Наружу отдаётся ссылка типа `Able`. Это и есть «кэшированный объект»: тот же объект с точки зрения вызывающего кода, но вызовы идут через обёртку.
2. Первый `a.method()` — метод ещё ни разу не считали. Обёртка вызывает настоящий `A.method()`. Тот печатает `original method`. Результат запоминается.
3. Второй `a.method()` — с прошлого раза объект не меняли. Обёртка настоящий метод не вызывает. Поэтому строка `original method` на экран не попадает. Для `void`-метода «вернуть прошлый результат» значит просто ничего не делать.
4. `a.setValue()` — это не кэш. Это метод, который меняет состояние. Он помечен `@Setter`. Он всегда выполняется по-настоящему и печатает `seter method`. После успешного вызова обёртка забывает всё, что запомнила.
5. Второй `a.setValue()` тоже выполняется по-настоящему. Сеттеры не кэшируются. Каждый вызов снова печатает `seter method` и снова очищает кэш.
6. Следующий `a.method()` снова идёт в настоящий метод, потому что кэш уже пустой. Снова печатается `original method`.

Если бы у `method()` был возвращаемый результат, например `int`, обёртка в первый раз вызвала бы метод и сохранила число. Во второй раз вернула бы это число, не вызывая метод.

## Две аннотации — это только метки

`@Cache` и `@Setter` сами ничего не делают. Это ярлыки на методах, которые ваша обёртка умеет прочитать во время работы программы.

- `@Cache` значит: «результат этого метода можно запоминать».
- `@Setter` значит: «этот метод меняет объект так, что старые результаты уже нельзя использовать».

Обе аннотации вешаются на метод и должны быть доступны во время выполнения: 
`@Target(ElementType.METHOD)` и `@Retention(RetentionPolicy.RUNTIME)`.

Аннотации не переписывают объект и не обнуляют его поля. 
Обнулять поля не нужно. `@Setter` только сообщает обёртке: «кэш больше не действителен, выброси его».

## Правила, по которым работает обёртка

Кэшируются только методы без параметров. 
Так задание упрощает задачу: не нужно думать, что результат зависит от аргументов.

На каждый вызов обёртка смотрит, какая аннотация висит на методе класса, и действует так.

Метод с `@Cache`:

- вызывают первый раз — выполнить настоящий метод и запомнить результат;
- вызывают снова, а сеттер с тех пор успешно не вызывали — настоящий метод не трогать, вернуть запомненное;
- вызывают снова, но сеттер уже успешно отработал — кэш пуст, снова выполнить настоящий метод и запомнить новый результат;
- настоящий метод бросил исключение — ничего не запоминать. В следующий раз метод надо вызвать снова. Ошибку не сохраняют и не повторяют её из кэша.

Метод с `@Setter`:

- всегда вызывать настоящий метод;
- если он завершился нормально — стереть кэш всех методов сразу;
- если он бросил исключение — кэш не трогать. Считаем, что состояние объекта не изменилось, раз метод не доработал.

Остальные методы обёртка просто пропускает в оригинальный объект.

## Что студент делает рефлексией в этом задании

Метод `cache` один. Классов, которые через него прогонят, много, и их код студент не правит. На каждый пришедший объект рефлексия отвечает на четыре вопроса.

Какой это класс на самом деле. `object.getClass()` возвращает `A`, даже если переменная объявлена как `Able`. Аннотации читают с этого класса.

Какие у него методы и какие на них стикеры. Список методов берут у класса. На каждом методе спрашивают, есть ли `@Cache` или `@Setter`.

Вызывать оригинал или отдать память. Это решает уже ваш код. Если надо вызвать оригинал, вызов идёт через `method.invoke(originalObject)`. Имя `method` в утилите нигде не написано: его приносит прокси в момент вызова.

Какие интерфейсы реализовать у обёртки. `getInterfaces()` говорит, что объект снаружи должен уметь то же, что `Able`. `Proxy.newProxyInstance` собирает такой объект. С этого момента `a.method()` попадает в ваш обработчик, а обработчик уже рефлексией смотрит аннотацию и при необходимости вызывает настоящий метод.

## Почему это делается через прокси

Обычный объект нельзя незаметно подменить: если у вас в руках `new A()`, вызов `a.method()` всегда попадёт в код класса `A`.

Поэтому `cache` возвращает не тот же экземпляр, а динамический прокси. Прокси — это объект, который снаружи умеет те же методы, а внутри на каждый вызов запускает ваш код. В этом коде вы и решаете: позвать оригинал или отдать значение из памяти. Сам прокси — часть рефлексии: класс обёртки появляется во время выполнения, а не написан вами заранее под `A`.

Схема такая:

```text
вызывающий код
    вызывает a.method()
        попадает в вашу обёртку
            обёртка смотрит аннотации метода на классе A
            если есть свежий кэш — возвращает его
            если нет — вызывает настоящий A.method() и запоминает результат
```

Искать аннотации один раз при создании обёртки и на этом остановиться недостаточно. 
Аннотация сама по себе метод не кэширует. Решение принимается в момент вызова.

## Важная деталь про интерфейс и класс

В примере метод вызывают через интерфейс `Able`, а аннотации висят на классе `A`.

Если спросить аннотацию у метода интерфейса, её там нет:

```java
Able.class.getMethod("method").isAnnotationPresent(Cache.class); // false
```

Аннотация написана в классе `A`, на его методе `method`. Читать её нужно с метода класса, а не с метода интерфейса. Вызов при этом может идти и через `Able`, и через `A` — обёртка всё равно смотрит на класс реального объекта.

Наследование в этом задании учитывать не нужно. Статические поля и методы тоже не нужны.

## Что приложить к решению

Тесты, которые проверяют поведение из примера и правила выше. Имеет смысл отдельно проверить:

- первый вызов выполняет метод;
- повторный вызов не выполняет метод и возвращает тот же результат;
- успешный `@Setter` заставляет следующий вызов снова выполнить метод;
- исключение из `@Cache`-метода не запоминается;
- исключение из `@Setter` не стирает кэш;
- аннотация читается с класса, даже если ссылка имеет тип интерфейса.

# Задание 2. Свой маленький тестовый фреймворк

## О чём это

JUnit делает три вещи: вы помечаете методы аннотациями, фреймворк сам их находит и запускает, потом сообщает, какой тест прошёл, а какой нет.

Нужно сделать то же самое в миниатюре. Готовый JUnit использовать как образец поведения можно. Сдавать нужно свой код.

Рефлексия здесь нужна по той же причине, что и в кэше. `runTests` принимает любой класс. Внутри `TestRunner` нет имён `testSum` или `testLogin`. Их находят уже у переданного класса.

Студент рефлексией:

- получает методы класса и оставляет те, на которых есть `@Test`, `@BeforeEach`, `@AfterEach`, `@BeforeSuite`, `@AfterSuite`, `@Disabled`, `@Order`;
- читает из аннотации имя теста и число приоритета;
- проверяет `Modifier.isStatic`, чтобы поймать неверно повешенную аннотацию и бросить `BadTestClassError`;
- создаёт объект тестового класса через конструктор: `newInstance()`;
- запускает метод через `method.invoke(...)` и смотрит, чем вызов закончился: нормально, `TestAssertionError` или другое исключение.

## Точка входа

Класс `TestRunner` с методом:

```java
public static Map<ResultType, List<TestResult>> runTests(Class<?> clz);
```

На вход — класс, в котором лежат тесты. На выход — карта: тип результата и список тестов, которые так закончились.

`ResultType`:

- `Success` — тест прошёл;
- `Failed` — проверка в тесте не сработала;
- `Error` — тест упал с обычным исключением, это не провал проверки, а поломка самого теста;
- `Skipped` — тест в списке есть, но его не запускали.

`TestResult` для каждого теста хранит:

- тип результата;
- имя теста;
- исключение, если оно было.

## Аннотации

Все методы тестов и методы «до» и «после» — без параметров.

- `@Test` — этот метод надо запустить как тест. В аннотации можно задать имя. Если имя не задано, именем теста считается имя метода.
- `@Disabled` — ставится рядом с `@Test`. Тест попадает в отчёт как `Skipped` и не выполняется.
- `@BeforeEach` и `@AfterEach` — обычные методы. Выполняются перед каждым запущенным тестом и после него.
- `@BeforeSuite` и `@AfterSuite` — только статические методы. Один раз перед всеми тестами и один раз после всех.
- `@Order` — приоритет теста. `10` выполняется раньше всех, `0` позже всех. Одинаковый приоритет сортируется по имени. Если приоритет не указан или указан неверно, он равен `5`.

## Как запускать и какие ошибки считать разными

Сначала проверяется сам тестовый класс.

- Нельзя создать объект класса — бросить `BadTestClassError` с понятным текстом.
- `@Test`, `@BeforeEach` или `@AfterEach` висят на статическом методе — `BadTestClassError`.
- `@BeforeSuite` или `@AfterSuite` висят на обычном, нестатическом методе — `BadTestClassError`.

Дальше тесты идут по порядку приоритета.

- Тест бросил `TestAssertionError` — это `Failed`. Условие проверки не выполнилось.
- Тест бросил любое другое исключение — это `Error`.
- Тест завершился без исключения — это `Success`.

Разница `Failed` и `Error` такая же, как в обычных тестах. `assertEquals` не сошёлся — тест провален. `NullPointerException` посреди теста — тест сломан.

Мелкие детали, которые в тексте не расписаны, можно решить по-своему. На собеседовании это решение нужно уметь объяснить. Если сомневаетесь, посмотрите, как это устроено в JUnit или TestNG.

# Что будут спрашивать на собеседовании

Вопросы крутятся вокруг того, что вы написали. Имеет смысл заранее проговорить себе ответы.

1. Как изменится кэш, если у методов появятся параметры. Сейчас ключ кэша — это сам метод. С параметрами одного метода мало: результат `sum(1, 2)` и `sum(3, 4)` разный. Ключом становится метод вместе с аргументами.
2. Чем вызов через класс отличается от вызова через интерфейс. Метод один, но аннотация лежит только на методе класса. У метода интерфейса её не видно, поэтому читать аннотацию надо с класса реального объекта.
3. Почему трудно понять, что объект изменился. Поле можно поменять напрямую, из другого метода без `@Setter`, из вложенного объекта. Задание сознательно упрощает это: изменением считается только успешный вызов метода с `@Setter`.
4. Как залогировать вызов любого метода любого класса, не дописывая `println` в каждый метод. Та же идея, что в задании 1: обёртка перехватывает вызов и пишет лог до или после оригинального метода.
5. Как запретить рефлексии ломать инкапсуляцию. Через модули Java и `SecurityManager` в старых версиях. Имеется в виду, что `setAccessible(true)` позволяет читать private-поля, и это можно ограничить.
6. Какой `Retention` у аннотаций этой работы и почему. `RUNTIME`. Если поставить `SOURCE` или `CLASS`, во время выполнения `isAnnotationPresent` аннотацию уже не увидит, и обёртка не сможет на неё опираться.
